## From Plan B2 (background audio) — 2026-08-27

B2 shipped 2026-08-27 (`8c6933f7..ae7ce62a`: itag 140 + live manifest TTL, audio session/interruptions/routes, background-play + audio-only, Now Playing + remote commands, PiP, rate-limiter gate + pre-emptive foreground re-resolve, acceptance pass). Open items its successors must handle:

- **CF-B2-1** PiP survives BACKGROUNDING, not a back-navigation out of the player: popping `PlayerScreen` releases the `@State PlayerViewModel` and the `AVPlayer` with it, so the floating window dies with the route. `PlayerHostView.Coordinator.deinit` now hands the audio session / Now Playing / remote commands back when that happens (the leak backstop), but the window itself still closes. Making PiP outlive the route needs an **app-scoped player holder** — one owner above the navigation stack that the host borrows from. → Plan B5 (it is the same holder Up Next / queue playback needs).
- **CF-B2-2** `StreamResolving.resolve(_:purpose:kind:sourceChannelId:forceRefresh:)` now carries a `RequestKind`, and `RateLimitedResolver` turns `.blocked`/`.delayed` into `.cooldown(until:)`. B2 uses `.player` (open/retry), `.autoRecovery` (recovery ladder) and `.proactiveTTLRefresh` (TTL refresh) — **`.prefetch` is unused and is B5's lane**. Two rules for the Up Next implementer: a `.prefetch` refusal must be **skipped silently** (never surfaced as `.cooldown`, never retried into), and auto-advance must **never pass `forceRefresh: true`** — the next video's manifest cache entry is the whole point of prefetching it. → Plan B5
- **CF-B2-3** `PlayerViewModel.resolve(…, silent:)` holds the current `StreamState` on the way OUT: a silent resolve that fails is dropped on the floor (`if silent, !result.isPlayable { return }`) so a background refresh can never kill a healthy playing stream — reactive recovery owns real failures. It is NOT the same flag as `showLoading:`, which only holds the state on the way IN. B3's embed rung must pass `silent: true` for any refresh it performs *while something is playing*, and must NOT pass it for a user-visible load whose failure has to be shown. → Plan B3
- **CF-B2-4** `PlayerHostView.applyBackgroundController`'s `onPolicyAction` closure reads **`model.state` live at action time**, not a captured copy — the pre-emptive re-resolve settles between the foreground notification and the `.restoreVideo` it produces, and a captured state would restore the URL the refresh just replaced. `applyPolicyAction` only acts on states `StreamState.resolved` understands (`.ready` / `.rung2Progressive`). If B3's embed rung is a new `StreamState` case, it falls through that switch harmlessly; if B3 instead models the embed *outside* `StreamState`, this closure and `PlayerViewModel.audioOnlyAvailable(for:)` both need revisiting. → Plan B3
- **CF-B2-5** `MPNowPlayingInfoPropertyMediaType` stays `.video` while audio-only is active (controller ruling, Task 4). The lock screen therefore renders an audio-only session with the video treatment. Cosmetic; flip it to `.audio` (and re-check the artwork/scrubber rendering that follows from it) as a follow-up if it looks wrong on hardware. → unowned follow-up
- **CF-B2-6** Test debt (T1-1, Task 1 review): `PlayerResponseParser` has no case for a **cipher-only** `adaptiveFormats` entry (`signatureCipher` present, `url` absent). The behaviour was verified by reading — `decodeIfPresent` yields `url: nil` and the entry is skipped — but nothing pins it, so a decoder change could start handing back a URL-less itag 140. → Plan B3 or any plan touching the parser
- **CF-B2-7** `BackgroundPlaybackController.willEnterForeground()` awaits `onWillEnterForeground` on a **best-effort** basis: the wait is bounded by `foregroundRefreshDeadline` (2 s), and when the deadline wins, `handle(.willEnterForeground)` runs **anyway** while the hook is still in flight. So the ordering is a preference, not a guarantee — **nothing may depend on the hook having completed** by the time the lifecycle policy runs. (`.restoreVideo` is safe under that rule precisely because it performs no swap of its own; the foreground `updateUIViewController` pass does the single replace, against whatever `Resolved` is current when it runs — a late refresh included.) B3 must not chain slow work onto the hook either: anything that isn't the TTL refresh belongs after `handle(.willEnterForeground)`, not inside the awaited closure, because past the deadline it is racing the policy rather than preceding it. → Plan B3
- **CF-B2-8** `BackgroundPlaybackController.detach()` calls `AVAudioSession.setActive(false, options: .notifyOthersOnDeactivation)` unconditionally. Once the embed rung (B3) or Shorts (B4) also owns audio, exactly one owner must deactivate the session, or leaving one player will silence the other. → Plans B3 / B4
- **CF-B2-9** `NowPlayingSnapshot.make` returns `nil` for `.embed` states, so backgrounding the embed rung leaves a stale Now Playing entry. B3 must clear it when the embed takes over (the embed is paused on background anyway — plan §6.4 row 3 — so "clear it" is the correct behaviour). → Plan B3
- **CF-B2-10** iPhone **landscape**: the player toolbar sits below the fold and the tab bar floats over the video (observed across the Task 7 screenshot matrix; pre-existing from B1, not introduced by B2). Landscape playback needs its own overlay treatment — full-bleed video, chrome that auto-hides, no tab bar. → Plan B5
- **CF-B2-11** The iPad `playerMaxWidth` screenshot assertion is **vacuous** — it passes without constraining anything, so a regression in the iPad player's max width would not be caught. Give it a real bound (or delete it and assert the constraint where it is applied). → Plan B5
- **CF-B2-12** ~~`.restoreVideo` performed a synchronous `replaceCurrentItem` *and* scheduled the foreground update pass, which replaced a second time against a possibly newer `Resolved` — the second replace restarts playback from 0.~~ **FIXED here (`ae7ce62a`)**: `applyPolicyAction` swaps synchronously only for `.swapToAudioOnly`; the restore is one replace, owned by the update pass.
- **CF-B2-13** ~~Auto-PiP and `didEnterBackgroundNotification` have no defined order, so the background swap could land first and AVKit would open the PiP window over an audio-only item — a black window.~~ **FIXED here (`ae7ce62a`, completed in fix round 2)**: `playerViewControllerWillStartPictureInPicture` calls `BackgroundPlaybackController.undoAutoSwapIfAny()`. Device checklist item 17 is the confirmation on hardware.
- **CF-B2-14** The periodic time observer is removed when the host is dismantled while PiP is deferred (`stopObserving()` runs unconditionally in `dismantleUIViewController`, before the teardown policy defers the rest), so the **lock-screen scrubber freezes** for the remaining life of the PiP window — `refreshNowPlaying()` is driven by that one observer.
