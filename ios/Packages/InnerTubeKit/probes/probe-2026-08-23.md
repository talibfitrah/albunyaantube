## GVS / pot-token check — the ruling-18 trigger

**VISIONOS did NOT demand a poToken on its HLS**, for either the lecture or the live video. Every `streamingData` URL (HLS master, 720p segments, itag140 audio) worked with `serviceIntegrityDimensions` omitted entirely. ANDROID itag18 also needed no pot, for both the lecture and kids videos.

**This is NOT a blocker.** §6.12's trigger condition ("VISIONOS now demands a GVS/pot token on its HLS") was not observed. Ruling: **proceed** — spec §6.13's primary rung (`visionosHLS`) is alive.

## UA-mismatch finding — corrects the task's framing, confirms the plan's own prior evidence

Five UA-mismatch checks were run (720p HLS segment ×3 — lecture, kids N/A since no HLS, live; itag18 chunk ×2 — lecture, kids). **All five returned the same status as the matching-UA request** (200/206, no 403). CDN enforcement here is IP-bound (`rqh=1`, `ip=`, `expire=` per plan §4 row 21), not UA-bound.

This is not a new finding — it's a direct reproduction of plan §4 row 5, already marked "verified": *"CDN User-Agent enforcement on `rqh=1` URLs — Safari UA, `AppleCoreMedia/1.0.0` UA, Python default UA → all 200."* The task brief's phrasing ("a UA mismatch 403s googlevideo — test it") does not match either this probe or the plan's own existing evidence; I'm flagging the discrepancy rather than silently going along with it, per this repo's "proof, not assumption" rule. Sending the correct per-client UA remains correct practice (consistency with `clientVersion`, and unknown whether YouTube tightens this later), just not something a UA mismatch will currently 403 on.
